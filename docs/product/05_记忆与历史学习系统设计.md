# 05 · 记忆与历史学习系统设计

> 本文档定义 成竹 的三层记忆体系。这是相对 MiroFish 的**核心增量能力**：MiroFish 的图谱是"单次任务内的静态世界快照"，成竹 增加跨任务、跨会话的学习闭环——系统会记录每一次使用的成功、失败与用户评价，并据此优化后续流程，越用越默契。
> 依赖：Graphiti（graphiti-core）+ Neo4j 自托管（替代 MiroFish 的 Zep Cloud，境内数据不出境）；SQLite 存结构化反馈与规则。

---

## 1. 三层记忆总览

| 层 | 名称 | 载体 | 生命周期 | 回答的问题 |
|----|------|------|---------|-----------|
| L1 | 研究图谱 ResearchGraph | Graphiti graph（每项目一个 group_id：`project_{id}`） | 项目级，追踪订阅时持续增量 | "关于这个研究对象，我们知道什么、什么时候知道的、哪些已过时" |
| L2 | 用户记忆 UserMemory | Graphiti graph（group_id：`user_{id}`）+ SQLite 偏好表 | 跨项目永久 | "这个用户关注什么、喜欢什么样的报告" |
| L3 | 经验规则库 Playbook | SQLite 表 + 定期归纳的规则文本 | 系统级永久 | "过去哪些做法成功/失败，流程该怎么改" |

## 2. L1 研究图谱（继承 MiroFish，替换实现）

### 2.1 从 Zep Cloud 迁移到自托管 Graphiti

MiroFish 用 Zep Cloud 的 `graph.add`（写入 episode）与 `graph.search`（混合检索）。Graphiti 是 Zep 的开源内核，API 对应关系：

| MiroFish (zep-cloud SDK) | 成竹 (graphiti-core) |
|--------------------------|------------------------------|
| `zep.graph.add(graph_id, type="text", data=chunk)` | `graphiti.add_episode(group_id, episode_body=chunk, source=EpisodeType.text, reference_time=...)` |
| `zep.graph.search(graph_id, query, scope="edges")` | `graphiti.search(query, group_ids=[...])`（返回 edges/facts） |
| `zep.graph.search(scope="nodes")` | `graphiti._search` 配 NODE_HYBRID_SEARCH recipe（或 `graphiti.search_` 节点检索接口） |
| ontology 自定义实体/关系类型 | `add_episode(entity_types={...}, edge_types={...})` Pydantic 模型 |

封装要求：新建 `backend/app/utils/graph_client.py`，对上层暴露与 MiroFish `zep_tools.py` 相同粒度的方法（`quick_search / panorama / get_all_nodes / get_all_edges / get_entity_summary / get_graph_statistics`），使 03 文档中分析 Agent 的"图谱三件套"工具可以近乎原样移植 MiroFish 的实现。文本 LLM 统一走 DeepSeek OpenAI 兼容接口；Embedding 暂保留百炼 `text-embedding-v4`，两类凭证不得混用。

**重要实现注意**：graphiti-core 默认用 OpenAI 结构化输出；接百炼时使用其 OpenAI 兼容的 `OpenAIGenericClient`，并将并发 `SEMAPHORE_LIMIT` 设为 5 以内防止百炼限流。首次启动时调用 `build_indices_and_constraints()` 建索引。

### 2.2 投研本体（ontology）定义

MiroFish 由 LLM 针对任意题材动态生成 ontology；成竹 场景固定，**采用"固定核心本体 + LLM 补充"策略**（更稳、便于前端着色）：

实体类型（`backend/app/graphdef/entities.py`，Pydantic）：
- `Company`（股票代码、行业、市值区间）
- `Person`（职务、关联公司）
- `Disclosure`（公告/财报，字段：类型、报告期、披露日期、URL）
- `FinancialMetric`（指标名、报告期、数值、单位、同比）
- `Event`（事件类型：问询/处罚/并购/人事/回购/业绩预告…、发生日期）
- `Opinion`（券商观点，字段：机构、评级、日期 —— 与事实区分的关键类型）
- `Industry`、`Product`、`RiskFactor`

关系类型：`DISCLOSES`(公司→披露)、`REPORTS`(披露→指标)、`INVOLVES`(事件→公司/人)、`RATES`(机构→公司，属性=评级)、`COMPETES_WITH`、`BELONGS_TO`(公司→行业)、`SUPPLIES`(公司→公司)、`WARNS`(披露→风险因素)。

### 2.3 写入与时序增量

- 采集阶段：每张 EvidenceCard 转为一个 episode 写入（`reference_time = publish_time`，这是时序图谱生效的关键——**必须用信息的发布时间而非抓取时间**）。episode 文本模板：`[{source_type}|{source_name}|{publish_time}] {title}\n{excerpt}\n结构化字段: {structured}`。
- 追踪订阅重跑时：只写入 `publish_time > 上次运行水位线` 的新卡片；Graphiti 的 bi-temporal 机制自动让被新事实取代的旧边失效（invalid_at），这正是"追踪简报-变化与更正"章节的数据来源：查询 `invalid_at` 落在本期窗口内的边。
- 去重：EvidenceCard 以 `md5(url + title)` 为 dedup key，SQLite 表 `evidence_card` 记录已入图卡片，重复不写。

## 3. L2 用户记忆

### 3.1 偏好的两种形态

**结构化偏好**（SQLite 表 `user_preference`，确定性高、直接用于表单预填）：

| key 示例 | value 示例 | 来源 |
|----------|-----------|------|
| watch_symbols | ["300750","002594"] | 任务卡历史高频标的（近 10 个任务出现 >= 2 次即入） |
| watch_industries | ["电池","储能"] | 同上 |
| deliverable_style.broker_view | "table" | 用户对"券商观点"章节点踩+评语"只要表格" → 反思 Agent 解析 |
| report_length | "brief" | 多次评语含"太长了" |
| default_time_window | "1Q" | 任务卡历史众数 |

**语义偏好**（写入 `user_{id}` 图谱）：每次任务结束后，把「任务需求原文 + 章节反馈 + 对话追问记录」作为 episode 写入用户图谱。Planner 解析新需求时先做一次 `graphiti.search(query=新需求, group_ids=[user_id])`，把命中的历史事实（如"用户曾追问存货问题"→ 说明其关注营运资本）注入 Prompt。

### 3.2 应用点（必须全部实现，这是演示脚本 5 的支撑）

1. **任务卡预填**：新建任务页调用 `GET /api/memory/prefill`，返回 watch_symbols、default_time_window、deliverable 偏好，前端预填充；
2. **Planner Prompt 注入**：`{user_memory_context}` 槽位（03 文档）；
3. **分析 Agent 风格注入**：`{style_directives}` 槽位，由结构化偏好渲染为指令（如"'券商观点汇总'章节用 Markdown 表格呈现，不写长段落"）；
4. **偏好可见可删**："我的偏好"页展示全部条目，支持删除（写 tombstone，禁止再学回同一条目 7 天）。

## 4. L3 经验规则库（Playbook）——"越用越默契"的引擎

### 4.1 原始记录：任务全息日志

每次任务运行产出（06 文档有表结构）：
- `task_run`：任务卡、各阶段耗时、成本（LLM tokens、博查次数）、终态（success/partial/failed）；
- `tool_call_log`：每次工具调用的成败、耗时、降级、返回卡片数；
- `feedback`：章节级 👍/👎/评语、报告级 1-5 星、对话中的纠错性追问（对话 Agent 检测到用户说"不对/错了/漏了"时自动打标 `correction`）；
- `agent_log.jsonl`：继承 MiroFish 的过程日志（每个 Agent 的思考、工具调用、结果全量留痕）。

### 4.2 反思 Agent（Reflection Agent，离线批处理）

触发时机：每次任务收到反馈后 + 每日凌晨定时。流程：

1. 取最近未反思的 `task_run` 及其 feedback、tool_call_log、agent_log 摘要；
2. LLM 归因（系统 Prompt 见 03 文档 §Reflection）：产出 0-N 条候选规则，JSON 格式：

```json
{
  "rule_type": "style | routing | prompt_patch | source_health",
  "scope": "user | global",
  "target_agent": "planner | collector_news | analyst_summary | reviewer | ...",
  "condition": "当任务涉及财务对比时",
  "action": "同比/环比必须以表格呈现并标注计算口径",
  "evidence_run_ids": ["run_0012"],
  "confidence": 0.8
}
```

3. 写入 SQLite 表 `playbook_rule`，初始状态 `candidate`。

### 4.3 规则生效与淘汰（防止学坏，必须实现）

- 状态机：`candidate →(同类证据 >= 2 或用户在偏好页手动确认) active →(连续 3 次生效任务中反馈变差) retired`；
- 注入方式：各 Agent 构建 Prompt 时调用 `playbook.get_rules(target_agent, scope, user_id)`，取 `active` 规则按 confidence 降序最多 5 条，渲染进 `{playbook_rules}` 槽位；
- 硬边界：规则 action 文本在注入前过合规检查（09 文档黑名单），规则**只能改变呈现方式、检索策略、数据源路由，不能改变合规约束与引用要求**（这两类指令在 Prompt 中位于规则槽位之后并声明优先级更高）;
- routing 类规则示例落地：`source_health` 规则（"新浪财报接口近 7 日成功率 0.4 → 财报采集直接走东财"）由采集编排器在派发前读取，与 04 文档 §5 的健康度打分联动。

### 4.4 效果度量（演示与答辩用）

`GET /api/playbook/stats` 返回：规则总数/各状态数、命中次数、命中任务的平均星级 vs 未命中任务平均星级。前端"我的偏好"页做成小面板，直接支撑"越用越默契"的量化证明。

## 5. 与整体管线的接合点汇总（给执行 Agent 的检查清单）

| 时机 | 动作 | 实现位置 |
|------|------|---------|
| 任务创建 | 读 L2 预填任务卡；Planner 注入用户记忆+规则 | orchestrator.plan 阶段 |
| 采集派发 | 读 L3 routing 规则 + 数据源健康度选择工具与降级路径 | orchestrator.collect 阶段 |
| 证据入图 | EvidenceCard→episode 写 L1（reference_time=publish_time，去重） | graph_ingest 服务 |
| 分析/审校 | Prompt 注入 style 规则；图谱三件套查 L1 | analyst/reviewer 服务 |
| 报告交付 | 记录 task_run 终态与成本 | report_assembler |
| 用户反馈 | 写 feedback → 触发 Reflection → 产出候选规则；语义偏好写 L2 | feedback API handler |
| 追踪重跑 | 水位线增量写 L1；invalid_at 查询产出"变化与更正" | tracking_scheduler |
| 每日定时 | Reflection 批处理；健康度汇总 | cron（APScheduler） |
