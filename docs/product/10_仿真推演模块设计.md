# 10 · 仿真推演模块设计（Scenario Simulation）

> 定位调整说明：本模块在初版设计中被移除，现根据产品决策**恢复为核心功能**。理由：本产品的目标是"替代普通研究员的 Agent 体系"，而研究员的高阶工作正是"如果发生 X，市场会怎样"的情景思考——这恰好是 MiroFish 仿真引擎的本源能力（数字沙盘预演）。
> 本模块是 MiroFish OASIS 链路的**移植 + 场景重定向**：从"任意舆情事件仿真"重定向为"围绕某研究标的的市场情景推演"。合规边界：推演产出为**情景观察**，禁止指向性投资结论（详见 §7 与 09 文档增补）。
> 与主管线的关系：推演是研究任务完成后的**可选支线**，以研究图谱（L1）为种子世界，不影响摘要/对比/追踪主管线的交付。

---

## 1. 用户故事与入口

- 研究员读完成竹生成的《宁德时代季度跟踪》，在报告"风险与关注点"章节看到"公司预计 Q2 海外订单存在不确定性[E41]"；
- 点击该风险点旁的「推演此情景」（或报告页顶部「情景推演」按钮自由输入假设）；
- 输入/确认情景假设："假设公司 7 月发布业绩预告，海外收入低于市场预期 20%"；
- 系统基于研究图谱构建一个包含机构投资者、卖方分析师、财经媒体、散户、公司 IR 等角色的模拟市场舆论场，注入情景事件，推演 N 轮；
- 产出《情景推演观察报告》：舆论演化时间线、多空分歧图谱、关键传导链、情景观察（合规话术）；
- 用户可对推演世界中任意"居民"发起采访追问（继承 MiroFish 深度互动能力，演示强亮点）。

## 2. 推演管线（对齐 MiroFish 原管线，逐阶段标注复用来源）

| # | 阶段 | 执行体 | 复用 MiroFish | 改动 |
|---|------|--------|---------------|------|
| S0 | 情景设计 | ScenarioAgent（LLM） | 无（新增） | 见 §3 |
| S1 | 角色生成 | PersonaGenerator | `oasis_profile_generator.py` **移植** | 实体来源从"图谱全部可发声实体"改为"固定市场角色模板 × 图谱事实充实"（§4）；Zep 检索换 graph_client |
| S2 | 仿真配置 | ScenarioConfigGenerator | `simulation_config_generator.py` **移植** | 时间轴从"中国作息"改为"交易时段节奏"（开盘前/盘中/收盘后/夜间）；initial_posts 由情景事件生成 |
| S3 | 仿真运行 | SimulationRunner | `simulation_runner.py` + `simulation_ipc.py` + `scripts/run_twitter_simulation.py` **移植** | 默认**单平台**（广场模式，够用且省一半成本）；保留 parallel 为可选；actions.jsonl 监控、run_state.json、文件 IPC 原样保留 |
| S4 | 记忆回写 | GraphMemoryUpdater | `zep_graph_memory_updater.py` 移植换底 | 写入独立推演图谱 `scenario_{id}`（不污染研究图谱 L1）；Zep graph.add → graphiti add_episode |
| S5 | 推演报告 | ScenarioReportAgent | `report_agent.py` 骨架（已在 analyst.py 移植） | 固定大纲（§5）；**恢复 interview_agents 工具**（原样移植 zep_tools.interview_agents 的选人/出题/批量采访逻辑） |
| S6 | 深度互动 | 采访 + 报告对话 | `POST /interview/batch` + chat | 原样移植 |

依赖：`camel-oasis`（pip 包，本地运行）；文本角色统一走 DeepSeek，禁止复用百炼视觉 Key。MiroFish scripts 目录的运行脚本随移植保留于 `backend/scenario_scripts/`。

## 3. ScenarioAgent（情景设计 Agent）

- 文件：`services/scenario/scenario_agent.py`；模型：DeepSeek `deepseek-v4-flash` 非思考模式；单轮 chat_json。
- 输入：用户假设文本、研究图谱统计与相关事实（graph_client 检索 top30）、任务卡、`{playbook_rules}`。
- 输出契约 ScenarioConfig：

```json
{
  "scenario_title": "业绩预告低于预期情景",
  "hypothesis": "7月15日公司发布业绩预告，海外收入低于市场一致预期20%",
  "baseline_facts": ["E12","E41"],
  "injected_events": [
    {"round": 1, "type": "official_disclosure", "content": "公司发布业绩预告：...", "poster_role": "company_ir"},
    {"round": 3, "type": "media_report", "content": "财经媒体解读：...", "poster_role": "financial_media"}
  ],
  "agent_scale": 30, "max_rounds": 10,
  "counter_scenario": {"enabled": true, "hypothesis": "业绩预告符合预期"}
}
```

- 系统 Prompt 要点：情景必须锚定研究图谱中的真实事实（baseline_facts 必须给出证据 id）；注入事件的表述必须显式标注"假设"；`counter_scenario` 默认开启——**成对推演**（悲观/基准两个情景各跑一次）是本模块的合规设计核心，报告呈现的是两情景差异而非单一未来（§7）。
- 用户确认环节：ScenarioConfig 渲染为可编辑表单（同任务卡确认交互），用户可改规模/轮数/事件文案后启动。

## 4. 市场角色体系（替换 MiroFish 的自由人设）

固定 7 类角色模板（`services/scenario/personas.py`），每类含：行为倾向、信息获取习惯、发声风格、动作偏好权重：

| 角色 | 占比建议 | 行为特征要点 |
|------|---------|-------------|
| 机构投资者 | 10% | 谨慎、看数据、少发声多观察，转发权威信源 |
| 卖方分析师 | 10% | 快速解读、输出观点、互相引用 |
| 财经媒体 | 13% | 追热点、放大信息、标题化表达 |
| 资深个人投资者 | 20% | 有立场、引用财报细节、与分析师互动 |
| 普通散户 | 34% | 情绪化、跟风、易受媒体影响 |
| 公司 IR | 3% | 官方口径、澄清与回应 |
| 行业观察者 | 10% | 供应链/竞品视角发声 |

生成流程（移植 oasis_profile_generator 主体逻辑）：角色模板 × 研究图谱事实充实（如资深个人投资者的 persona 中写入"长期跟踪该公司存货与海外产能问题"——取自 L1 真实事实）→ LLM 生成个体 bio/persona → 落盘 twitter_profiles.csv。失败降级：模板直接实例化（规则引擎，零 LLM）。

## 5. 推演报告（固定大纲）

`执行摘要（情景设定重述）/ 舆论演化时间线（分轮次关键节点）/ 分歧图谱（多空/观望阵营分布与代表性言论，按角色分层）/ 关键传导链（信息如何从披露→分析师→媒体→散户扩散，引用 insight_forge 结果）/ 双情景对比（悲观 vs 基准情景的舆论差异）/ 情景观察与局限性（合规话术+模型局限声明）`

工具集：graph 三件套（指向 scenario 图谱）+ `interview_agents`（移植恢复）+ `graph_quick_search`（可跨查 L1 研究图谱以引用真实基线事实）。写作铁律在 03§A4 基础上增加两条：
1. 所有推演内容必须冠以"模拟情景中"限定语，与真实事实（[E*] 角标）严格区分——推演引用用 `[S*]` 角标（指向仿真 actions/采访记录）；
2. 禁止把仿真结果外推为现实预测（"模拟中散户情绪转空"可写，"股价将下跌"不可写）。

## 6. API 与数据（增补到 06 文档体系）

蓝图 `/api/scenario`（api/scenario.py）：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/create` | `{task_id, hypothesis, from_evidence_id?}` → ScenarioAgent 生成配置 → `{scenario_id, scenario_config}`（awaiting_confirm） |
| POST | `/{id}/start` | body=确认后的配置；启动 S1-S5 后台管线（复用 TaskManager 轮询协议） |
| GET | `/{id}/status` `/{id}/run-status` `/{id}/agent-log` | 轮询协议同主管线；run-status 含轮次进度与最新动作流（对齐 MiroFish run-status/detail） |
| POST | `/{id}/interview` | `{agent_id?, topic, max_agents}` → 批量采访（文件 IPC，需仿真环境存活；env-status/close-env 接口一并移植） |
| GET | `/{id}/report` | 推演报告（结构同主报告接口，sources 分 E/S 两组） |

持久化：`uploads/scenarios/{scenario_id}/`（scenario.json、profiles、twitter/actions.jsonl、run_state.json、ipc_*、report/），SQLite 增表 `scenario_run(scenario_id, task_id, config_json, status, cost, started_at, finished_at)`。推演结束后 `task_run` 机制同样记录成本与反馈（推演报告支持章节反馈，接入 L3 学习闭环）。

## 7. 合规设计（本模块的红线，Reviewer 强制执行）

1. **成对推演**：默认跑悲观+基准双情景，报告核心是"差异观察"，结构上避免单一结论指向；
2. **限定语强制**：Reviewer 增加规则——推演章节中每个结论句必须含"模拟/情景/沙盘"限定词之一，缺失即 revise；
3. **禁止外推**：黑名单追加 `股价将|必然导致|应及时(买|卖|减持|加仓)`；
4. **显著性声明**：推演报告头部固定横幅文案（constants.py 增补）："以下内容为多智能体在假设情景下的模拟舆论演化观察，模拟世界不等于真实市场，不构成对任何真实事件走向的预测或投资建议。"
5. 局限性章节为必选章节，固定披露：agent 规模、轮数、模型偏差、情绪传播模型的简化假设。

## 8. 资源与成本（Demo 参数）

| 参数 | Demo 值 | 说明 |
|------|--------|------|
| agent_scale | 30 | 每情景 |
| max_rounds | 10 | 双情景共 20 轮 |
| 平台 | 单平台（twitter 广场模式） | parallel 保留为配置项 |
| LLM 调用 | 约 30×10×2 ≈ 600 次（deepseek-v4-flash） | 推演为独立重任务，启动前单独展示成本预估 |
| 时长 | 15-25 分钟 | 前端需明确预期管理（07 文档 UX） |

推演属重操作：单任务同时只允许 1 个运行中情景；`SCENARIO_ENABLED=true`、`SCENARIO_AGENT_SCALE`、`SCENARIO_MAX_ROUNDS` 入 .env。
