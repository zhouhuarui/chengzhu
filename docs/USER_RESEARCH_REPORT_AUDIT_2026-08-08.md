# 成竹 Foresketch 用户视角全功能测试与升级建议

- 测试日期：2026-08-08
- 测试目标：判断当前产品是否能满足单个研究员从提出需求到完成、审定并交付研报的需要
- 测试方式：隔离演示数据上的真实后端/API 用户旅程、现有自动化回归、前端实现审查、演示报告与图表内容核验
- 重要限制：本次无法取得合格的当前界面截图。Codex 应用内浏览器不可用，Chrome 未安装 ChatGPT Chrome Extension；因此配色、字体、间距、实际断点布局和完整键盘操作仍需补一次真实浏览器截图审计。本文不会把静态代码推断当作已确认的视觉结论。

## 1. 最终结论

**当前不满足“研究员在系统内独立完成正式研报”的完整需要。**

产品已经具备较好的研究基础设施：自然语言任务卡、证据卡、不可变 Run、引用角标、直接分析/证据辩论、审校、团队事件、追踪和情景推演框架。它适合：

- 产品演示和合成案例回放；
- 研究资料收集、整理与溯源；
- 生成一份可审阅的只读初稿；
- 展示多 Agent 的过程与合规门禁。

它暂不适合：

- 在当前本地开发配置中稳定完成一次真实研究；
- 在产品内编辑、重写、合并和定稿正文；
- 管理引用、数据底稿、图表和版本差异；
- 导出符合正式交付要求的 DOCX/PDF；
- 把当前图表直接用于严谨的财务判断；
- 把当前情景推演当作可信的基本面分析。

更准确的定位是：**“带可追溯证据链的投研初稿与审计原型”，而不是“完整研报写作工作台”。**

## 2. 测试范围与环境

本次使用临时 Uploads/SQLite 副本启动当前工作区代码，未覆盖开发者原有任务数据。当前环境状态：

- 前端、后端和 Neo4j 可启动；
- 文本模型、视觉模型、Bocha、Datayes 未配置；
- AgentTeams Controller、Matrix、MinIO/MCP 完整运行栈未就绪；
- 合成 replay 案例可完整读取；
- 新建真实任务可完成解析和任务卡确认，但在 AgentTeams 派发阶段失败。

当前仓库已有大量未提交改动，本次将其视为待测产品现状；除本报告外未修改业务代码。

## 4. 用户旅程逐步健康度

| 步骤 | 用户看到/要完成的任务 | 健康度 | 结论 |
| --- | --- | --- | --- |
| 1 | 首页输入研究需求、选择示例、上传材料 | 部分健康 | 入口简洁；非法/过大文件被静默忽略，历史状态和失败反馈不足 |
| 2 | 核对任务卡、标的、日期、信息源与研究模式 | 部分健康 | 字段基本齐全；缺日期倒置、重复标的、空信息源、证券真实性校验 |
| 3 | 点击“开始研究” | 不健康（当前环境） | 会进入 AgentTeams 派发失败，错误为技术性 `AgentTeamsClientError`，用户没有可行动的修复指引 |
| 4 | 查看管线、日志、团队、辩论、证据和图谱 | replay 健康、live 未证明 | 过程透明度是优势；图谱最大化无效、失败诊断和审批发现性不足 |
| 5 | 打开并阅读报告 | 部分健康 | 历史报告和引用结构可读；正文只读，无法形成正式写作闭环 |
| 6 | 阅读表格和图表 | 不满足正式使用 | 存在 `None`、时间窗外数据、累计期间平滑连线和缺少口径/单位等风险 |
| 7 | 点击证据、审校、辩论与 Run | 部分健康 | 溯源框架好；证据加载竞态、跨 Run 聊天串上下文等会破坏可信度 |
| 8 | 追问报告并应用修改 | 不满足 | 无 Key 演示连报告中明确数字也回答“无匹配证据”；回答不能一键写回正文 |
| 9 | 反馈并让系统学习偏好 | 基础可用 | 反馈和规则 API 可用；章节反馈位置错误，学习逻辑和可解释性较浅 |
| 10 | 建立持续追踪 | 不健康 | 基础订阅可用；“立即重跑”90 秒仍无响应、最终约 5 分 40 秒才完成，无进度/取消/可靠通知 |
| 11 | 情景推演与角色采访 | 实验性、不宜用于判断 | 能生成模板报告，但分支 Tab、停止、角色选择等交互与真实行为不一致 |
| 12 | 导出并正式交付 | 不满足 | 只有 Markdown；缺 DOCX/PDF、目录、分页、脚注、图表图片和版式验收 |

## 5. 已确认的产品优势

1. **证据和 Run 的架构方向正确。** 冻结证据、不可变运行、引用映射、审计与发布门禁，适合高可信研究产品。
2. **直接分析与证据辩论区分明确。** replay 中可查看通过、驳回、撤回、未决观点，避免把原始思维链暴露给用户。
3. **过程透明。** 管线、Agent 日志、团队 DAG、事件、成本和降级信息为故障定位与审计提供基础。
4. **报告内容经过确定性门禁。** 后端测试覆盖引用、财务口径、图表数值、claim gate、审批和回滚等关键约束。
5. **Markdown 导出有数据降级设计。** 主导出接口会把图表转为可读表格，优于直接丢失图表数据。
6. **合规边界较清楚。** replay、合成数据和情景模拟包含非投资建议说明。

## 6. 最高风险问题

### P0-1：当前真实用户旅程在研究启动处中断

项目健康接口能显示模型/AgentTeams 配置状态，但任务确认页在用户点击前不做可理解的就绪检查。本次实际确认任务后，pipeline 进入 `failed`，原因是 AgentTeams 派发失败。

影响：用户完成输入和校对后才发现系统不可用，且不知道缺少哪个服务、是否可重试、是否可改用本地模式。

建议：在任务确认页提供“运行就绪卡”，逐项显示数据源、模型、AgentTeams、MCP、存储与预算；不满足时禁用开始按钮并给出具体下一步。

### P0-2：报告不是写作工作台

报告页只有阅读、聊天、反馈、追踪、推演和 Markdown 下载，没有：

- 正文和提纲编辑；
- 段落锁定、接受/拒绝 AI 改写；
- 自动保存、撤销/重做；
- 证据增删、引用替换和缺失引用检查；
- 草稿、审核、定稿状态；
- Run diff 与版本合并；
- DOCX/PDF 正式导出。

这不是视觉润色问题，而是目标用户完成核心工作的能力缺失。

### P0-3：报告就绪、证据和跨 Run 状态有可信度缺陷

- 状态先完成、报告稍后就绪时，“重新检查”只重查状态，不再检查报告，页面可能永久打不开报告；
- 正文证据组件可能在证据索引加载前挂载，索引到达后不会重新挂载；
- 切换历史 Run 不清空聊天记录，新 Run 会携带旧 Run 对话上下文；
- 快速切 Run 没有请求取消或序列保护，慢响应可能覆盖当前选择；
- 所有章节反馈控件堆在全文之后，用户不知道自己在评价哪一章。

这些问题直接影响“我看到的报告、证据和问答是否属于同一个 Run”。

### P0-4：图表和表格会制造错误理解

实际演示报告中确认了以下问题：

- 财务表包含多个 `None 亿` 行；
- 任务要求近期数据，表格却混入 1998–2002 年记录；
- “归母净利润走势”把 FY、Q1、H1、Q3 等累计值按日期平滑连线；
- Q1/H1/Q3 累计值自然递增，跨年又重置，连线不代表经济意义上的连续趋势；
- 图中没有独立的轴单位、币种、期间类型、累计/单季口径和比较基准；
- 单序列没有 legend，多序列柱图也没有完整 legend；
- 固定 320px 高度，没有 resize、dataZoom、标签避让和无障碍表格；
- 无效 chart JSON 会静默消失；来源只是文本，不能打开证据。

好的引用门禁不能弥补错误的图表语义。对研报用户而言，这属于 P0 数据表达风险。

### P0-5：上传边界前后端不一致

前端会静默过滤不支持格式；后端则没有执行同一扩展名白名单。本次直接上传 `package.json` 得到 200，文件实际被保存。

同时，前端文案给人的印象是“每个文件 ≤50MB”，但 Flask 50MB 是整个请求上限，多文件时预期不一致。

建议：后端做 MIME、扩展名、魔数和总大小校验；前端逐文件显示接受/拒绝原因、数量和总大小，并在授权文件变化时重新确认云处理同意。

### P0-6：追踪“立即重跑”是同步长请求

实际请求 90 秒没有返回；后端继续串行/重试多个公网工具，约 5 分 40 秒后才完成。前端没有 busy、防重复点击、进度、取消或错误提示，而全局 Axios 超时是 300 秒，因此用户很可能先看到超时失败、后台稍后却又生成简报，形成前后状态不一致。

建议：`run-now` 立即返回 202 + job_id，后台队列执行；前端展示数据源级进度、失败、取消和完成通知。

### P0-7：情景推演的界面承诺与实际行为不一致

已确认：

- 悲观/基准 Tab 只改变选中样式，没有按 branch 过滤动作；
- “停止推演”只停止前端轮询，后台继续执行；
- 角色被选中后，selectedChar 没有发送给采访 API；
- 失败会停止轮询，但页面没有可靠失败态；
- 从报告创建后重新提交配置，生成的报告标题可以为空；
- 本次“原材料成本上升 10%”推演主要生成通用情绪传播模板，并未完成两家公司现金流韧性分析。

在修复和重新建模前，应持续标注为“实验性舆论沙盘”，不要放在正式研报核心流程中。

### P0-8：发布审批存在发现性和防误触问题

审批藏在默认未选中的 AgentTeams Tab 中；“批准并发布”没有最终确认，驳回理由不是必填，回滚前也没有差异预览。对不可变报告而言，这些操作需要更强的决策上下文。

## 7. 易用性、响应式与可访问性风险

以下为代码可确认或高概率风险；仍需真实浏览器验证：

- 上传区、历史任务卡、订阅卡、知识图谱节点等不是完整键盘控件；
- 多数弹层缺少 `role=dialog`、`aria-modal`、焦点锁定、Escape 和关闭后焦点恢复；
- ECharts Canvas 没有 aria、文字摘要或等价数据表；D3 SVG 没有可访问名称和键盘操作；
- 小号证据角标和多处 muted 文本对比度偏低；
- 没有统一 `:focus-visible` 和 `prefers-reduced-motion`；
- 顶栏没有移动端收口；报告 + 340px 聊天栏、380px 推演抽屉、偏好页表格、320px 图谱详情在窄屏容易溢出；
- 语言开关存在，但当前可达页面绝大多数文案仍硬编码中文，会形成中英混排；
- 运行失败后标题仍是“任务运行中”，很多 API 失败被降级成“暂无数据”，用户无法区分空状态与系统故障；
- 完成后 3 秒自动跳转，没有暂停，可能打断日志阅读和辅助技术用户。

本次不能声称符合 WCAG；建议以 WCAG 2.2 AA 为产品目标，并补真实键盘、VoiceOver/NVDA、200%/400% 缩放测试。

## 9. 升级建议方案

### 阶段 A：真实、可恢复、不会串数据（P0，建议 1–2 个迭代）

目标：让一次真实研究能够稳定完成，并让用户始终知道系统、任务、报告和 Run 的真实状态。

工作项：

1. 增加前置运行就绪检查和可行动错误；区分 live/replay/synthetic/heuristic/degraded。
2. 完成一条真实 AgentTeams + 数据源 + LLM + 审批 + 发布 E2E；把外部服务按 mock、sandbox、live 分层测试。
3. 修复报告就绪重试、证据加载竞态、跨 Run 聊天、快速 Run 切换竞态和章节反馈位置。
4. 上传校验统一放在服务端；客户端逐文件展示结果。
5. 追踪改为异步 job；提供进度、取消、幂等、防重入和失败重试。
6. 修复审批确认、驳回理由、回滚差异预览和审批待办入口。
7. 情景模块修复分支、停止、失败、角色定向和标题；在此之前明显标注“实验性”。
8. 统一 error/empty/loading/stale 状态，不再把接口错误显示成“暂无”。

验收标准：

- 当前运行所需服务缺失时，用户在点击前即可看到具体缺项；
- 真实测试环境从创建任务到批准发布完整跑通；
- 页面刷新、服务重启和报告延迟提交后均能恢复；
- 快速切换 Run 不发生报告、证据、聊天、反馈串线；
- `run-now` 在 1 秒内返回 job_id，不再占用数分钟的前台请求；
- 禁止格式、超限和重复文件均得到明确提示，后端不可绕过。

### 阶段 B：研报写作工作台（P0/P1，建议 2–3 个迭代）

目标：把“只读初稿”升级成用户可以真正完成的研报。

工作项：

1. 结构化章节编辑器：目录、正文、表格、图表、脚注、免责声明。
2. 章级 AI 操作：重写、缩写、展开、应用追问结果、接受/拒绝 diff。
3. 自动保存、撤销/重做、段落锁定、草稿/审核/定稿状态。
4. 引用管理器：搜索证据、补充/排除/锁定、替换引用、缺失引用检查、原文页码。
5. Run 差异：正文、事实、证据和图表的 side-by-side diff 与选择性合并。
6. 数据底稿：表格下载、来源、查询时间、口径和计算公式。
7. DOCX、PDF、Markdown 三类导出；支持目录、分页、页眉页脚、脚注、图表和机构模板。

验收标准：

- 用户能在不离开系统的情况下完成一篇报告的编辑、引用核验、审核和定稿；
- 每段关键结论可追溯到证据或明确标为分析判断；
- DOCX/PDF 在至少三种典型报告模板上通过页面渲染比对；
- 导出文件包含正确目录、页码、图表、来源和免责声明；
- 任意 AI 修改都有可审阅 diff，不能静默覆盖人工内容。

### 阶段 C：数据与可视化可信度（P0/P1，建议与阶段 B 并行）

目标：确保图表先正确，再漂亮。

工作项：

1. chart schema 强制：单位、币种、period_type、累计/单季、比较基准、fact_uid、source_refs。
2. 默认过滤 `None`、超出时间窗、重复和明显异常记录；需要保留时给出可见告警。
3. 不同报告期/累计口径禁止直接同图，除非用户明确选择并看到口径警示。
4. 财务序列默认不平滑；提供同口径同比、单季化或 TTM 视图。
5. 补轴标题、legend、数值格式、负数/百分比、标签避让、dataZoom 和下载数据。
6. 每张图提供可点击来源和等价数据表；无效图表展示错误而非消失。
7. 使用 ResizeObserver、`chart.resize()` 和 dispose；图谱采用稳定的业务语义颜色、搜索/筛选和列表替代视图。

验收标准：

- 图表中的每个值均可映射到唯一 fact_uid 与证据；
- FY/Q1/H1/Q3 累计值不再被默认画成平滑“趋势”；
- 单位、币种、期间、口径和来源无需 hover 即可识别；
- 320–1440px、200% 缩放和屏幕阅读器下均有等价信息；
- Markdown、DOCX、PDF 中图表数据一致。

### 阶段 D：日常效率、移动端与无障碍（P1/P2，建议 1–2 个迭代）

目标：让产品从演示可用升级到日常可用。

工作项：

1. 研究模板、公司覆盖列表、证券主数据校验、任务搜索/筛选/删除。
2. 可靠调度、邮件/企业消息通知、简报已读和时区/周几设置。
3. 移动导航、报告聊天、推演抽屉、表格和审批布局重构。
4. 完整键盘操作、dialog 焦点管理、live region、对比度、减少动画。
5. 如果无法完成双语覆盖，暂时隐藏语言开关；修正 HTML 标题与旧 MiroFish 品牌残留。
6. 拆分 ECharts/D3 等大依赖，按路由懒加载并建立性能预算。
7. 清理未路由的旧页面与无后端对应的旧 API，避免两套产品模型并存。

验收标准：

- 核心流程在 390、768、1440px 可用；
- 仅用键盘可完成创建、确认、阅读、编辑、导出和审批；
- 无严重/高等级无障碍缺陷；
- 首屏主包低于约定预算，图表和图谱按需加载；
- 调度重启不丢任务，重复点击不产生重复简报。

### 阶段 E：多人、权限与治理（P2，正式商业化前）

目标：从本地单用户原型升级到团队研究系统。

工作项：

- 登录、组织、角色、项目和数据隔离；
- 研究员/审核人/发布人权限分离；
- 批注、@协作者、变更记录、导出审计；
- 私有数据许可与外发策略；
- 备份、恢复、数据保留和删除策略。

## 10. 推荐的产品优先级调整

建议未来两个版本暂停继续增加新的 Agent 展示模块，把资源集中到：

1. **真实运行可靠性与可恢复性；**
2. **可编辑、可核验、可定稿的研报工作台；**
3. **正确的数据口径和可交付的图表/文档；**
4. **真实用户浏览器、移动端与无障碍验收。**

只有这四项完成后，Agent 数量、情景玩法和协作可视化才会转化成研究员愿意持续使用的价值。

## 11. 上线门槛建议

在对外声称“可用于研报写作”前，至少满足：

- 一条真实端到端研究链路连续稳定通过；
- 关键数据无 `None`、时间窗外混入和跨口径误图；
- 报告可编辑、可保存、可审核、可导出 DOCX/PDF；
- 每个关键数字可回到证据；
- 追踪异步、可取消、有通知；
- 情景模块要么完成真实性修复，要么清楚标为实验功能；
- 通过真实浏览器截图、响应式、键盘和屏幕阅读器测试；
- 具备最基本的用户身份与数据隔离。

在此之前，适合对外使用的表述是：

> 成竹是一套面向投研资料整理、证据溯源和可审计初稿生成的多 Agent 原型系统。
